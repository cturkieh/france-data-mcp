Automatiser le backfill BAN — supprimer la corvée hebdo, puis le pilote automatique

En une phrase : on donne à Ameli le même « bouton » qu'RPPS (en réglant d'abord la cause-racine qui m'oblige à intervenir à la main chaque semaine), puis plus tard on supprime le bouton des deux pour que tout parte tout seul après chaque mise à jour des données.

1 Le problème, en simple

Chaque semaine, un nouveau fichier Ameli arrive « nu » (adresses écrites, pas de coordonnées GPS). À l'arrivée, les adresses déjà connues récupèrent automatiquement leur position exacte depuis notre carnet d'adresses permanent (le cache). Les nouvelles, elles, restent au centre du village en attendant qu'on aille leur chercher des coordonnées : c'est le backfill.

Aujourd'hui, ce backfill est 100 % manuel pour Ameli : tu reçois un mail, tu me le transmets, et je dois faire une petite « réparation technique » à la main avant même de pouvoir lancer le géocodage. C'est cette réparation hebdomadaire qu'on veut supprimer.

La cause-racine Pour trouver vite les adresses à géocoder, Ameli s'appuie sur un « marque-page » (un index). Or, quand le nouveau fichier remplace l'ancien, le marque-page reste collé sur l'ancien fichier parti à la corbeille. Sans lui, le script relit les 485 000 lignes une par une → il plante au bout de 50 secondes. Je dois donc recréer le marque-page à la main à chaque fois.

2 Pourquoi RPPS a déjà un bouton, et pas Ameli

On a déjà rencontré et résolu exactement ce problème pour le RPPS. La différence tient à la façon de retrouver la liste des adresses à géocoder :

SourceComment elle trouve les adressesMarque-page ?État
RPPS (mensuel) Par numéro de ligne (un compteur interne toujours présent) Pas nécessaire 🟡 bouton GitHub
Ameli (hebdo) Par l'adresse elle-même → exige le marque-page fragile Détruit à chaque fichier 🔴 100 % manuel

Le « numéro de ligne » est toujours indexé d'office (c'est la clé primaire de la table). En s'appuyant dessus, RPPS n'a aucun marque-page à entretenir. Il suffit de faire pareil pour Ameli.

Avant / après — ce que change l'étape 1

// AUJOURD'HUI (Ameli) mail reçu → je recrée le marque-page À LA MAIN → je lance le script → cache rempli ▲ étape fragile, chaque semaine, nécessite Claude // APRÈS L'ÉTAPE 1 (Ameli, comme RPPS) mail reçu → tu cliques sur le bouton GitHub → cache rempli ▲ plus aucun marque-page, plus aucune réparation

3 Étape 1 — le bouton Ameli à faire maintenant

On réplique le mécanisme RPPS, déjà prouvé en production. Quatre petits chantiers :

1
Apprendre à Ameli à lister par numéro de ligne — une fonction base de données jumelle de celle d'RPPS (le « moteur de recherche » des adresses à géocoder, version sans marque-page).
2
Brancher le script dessus — 4 lignes à changer dans le script de backfill pour qu'il utilise ce nouveau moteur.
3
Créer le bouton GitHub Ameli — copie conforme du bouton RPPS, en version « Ameli ».
4
Filets de sécurité — un test automatique qui garantit que le moteur Ameli vise exactement les bonnes adresses (anti-régression silencieuse).
Le critère de réussite Lancer le bouton Ameli sans avoir recréé aucun marque-page au préalable, et que ça draine sans planter. Si ce test passe, la corvée hebdomadaire est éliminée pour de bon.

Effet concret pour toi : à la place du mail « lancer manuellement node… », tu auras juste un bouton à cliquer dans l'onglet Actions de GitHub. Exactement comme le RPPS aujourd'hui.

4 Étape 2 — le zéro-clic plus tard

Une fois les deux sources au niveau « bouton », l'étape suivante supprime le bouton lui-même : le drain se déclenche tout seul juste après chaque mise à jour des données (RPPS et Ameli). Plus de mail, plus de clic.

// ÉTAPE 2 — bout en bout, sans intervention nouveau fichier ingéré ✓ → le drain part automatiquement → cache rempli → posé au fichier suivant

Techniquement : on relie le drain à la fin réussie de l'ingestion (mécanisme natif GitHub « un workflow en déclenche un autre »). On garde l'ingestion (sensible) et le géocodage (best-effort) découplés : si le géocodage rate, l'ingestion santé reste verte.

Rappel — ce que le zéro-clic ne change pas Il supprime le clic, pas le décalage d'une passe : les nouvelles coordonnées sont toujours posées au fichier suivant (semaine pour Ameli, mois pour RPPS). Réduire ce décalage à zéro est un sujet séparé, qu'on n'ouvre pas ici.
