2 Les 3 fusions

A1 · lister_nomenclature tue la collision

lister_specialites_ameli
lister_types_ps_ameli
lister_specialites_medicales
→
lister_nomenclature(referentiel)

referentiel ∈ { ameli_specialites, ameli_types_ps, rpps_savoir_faire }. Un seul tool de découverte → plus de jumeaux à se masquer. Les cross-pointeurs anti-confusion ANS↔Ameli deviennent une section de la description unique.

A2 · population prépare l'IRIS

population_par_commune
population_par_departement
→
population(code)

Granularité auto-détectée par la forme du code : 5 car. = commune, 2-3 car. = département. En Phase B, 9 car. = IRIS s'ajoute sans nouveau tool. Retour PMUN/PCAP/PTOT inchangé ; caveats Mayotte & commune fusionnée préservés.

A3 · densite_sante

densite_professionnels_sante
densite_etablissements_sante
→
densite_sante(cible)

cible ∈ { professionnels, etablissements }. Le squelette dupliqué (scope dept/commune/nom_commune, PMUN, compare_national, garde-fou Paris/PLM) est mutualisé. Filtres conditionnels selon la cible (profession/savoir_faire vs famille).

3 Ce qu'on ne fusionne PAS

Frontière de la consolidation intelligente La famille *_in_radius (6 tools : entreprises, finess, centres_sante, professionnels, professionnels_rpps, coverage) reste séparée. Leurs filtres et sorties sont trop hétérogènes (catégories FINESS vs spécialités Ameli vs NAF SIRENE) — un méga-tool conditionnel deviendrait illisible pour le LLM = perte de qualité. Le partage se fait déjà au niveau du code, pas du tool.

4 Migration breaking — ⚠️ consommateurs (GEO Intel)

Rupture nette : les 5 anciens noms sont supprimés (0.x autorise le breaking documenté). À répercuter côté appelants :
