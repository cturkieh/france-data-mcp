# france-data-mcp V0.2 — Design specification

**Status** : approved by Cyril, ready for implementation plan
**Date** : 2026-05-07
**Author** : Claude (brainstormed with Cyril)
**Predecessor** : V0.1.0 in production at https://france-data-mcp.vercel.app/mcp

---

## 1. Objective

Extend `france-data-mcp` to cover the three public health/demography data sources missing from V0.1, and add a composite tool that produces a complete health panorama of a French territory in a single MCP call.

The success criterion is operational: reproduce the Charleville-Mézières (08105) territorial analysis end-to-end with deviations under 5% on every published indicator.

## 2. Scope

### In scope

- 3 new data sources ingested into a dedicated Supabase project with PostGIS:
  - **FINESS** (35 MB CSV, bimonthly) — health establishments (hospitals, EHPAD, MCO, SSR)
  - **Annuaire Santé Ameli** (146 MB CSV, weekly) — health professionals (doctors, nurses, midwives)
  - **INSEE Population IRIS** (49 MB CSV, yearly) — sub-municipal demographics by age and CSP
- 6 new MCP tools (see Section 5)
- Automated ingestion via GitHub Actions cron (one workflow per source, distinct cadences)
- 3-level validation pipeline (pre-validate, staging, atomic swap) guaranteeing zero production data degradation
- Read-only RLS policies on all production tables (anon role can only SELECT)
- Test pyramid (unit / DB integration / Charleville E2E reference) with CI running Supabase Local in Docker
- V0.1 technical debt remediation listed in the V0.2 memory note (branded types, JSON-RPC error codes, MCP server tests, discriminated union for `getEntrepriseBySiren`)

### Out of scope

- Geo Intel privé Unilabs (separate private project at `~/Developer/medterritoire`)
- npm package publication (`pnpm publish`) — can happen in parallel
- LinkedIn / data.gouv.fr announcement — post-delivery
- Rate limiting on the public MCP server — YAGNI for V0.2, hotfix if needed
- Threat modeling beyond the basic security stance described in Section 4

## 3. Architecture

### Overall data flow

```
GOVERNMENT SOURCES (data.gouv, ANS, Ameli)
  │  FINESS.csv (35 MB)  Ameli.csv (146 MB)  IRIS.csv (49 MB)
  ▼ bimonthly                weekly                yearly
GITHUB ACTIONS WORKFLOWS (3 crons)
  └─ download → pre-validate → COPY staging → validate → atomic swap
  ▼ (service_role key from GitHub Secrets)
SUPABASE DEDICATED PROJECT "france-data-public" (PostGIS)
  ├─ finess  (~80K rows)
  ├─ ameli   (~1.5M rows)
  ├─ iris    (~50K rows)
  └─ ingest_log (audit trail)
  ▼ (anon key + RLS read-only)
VERCEL SERVERLESS — api/mcp.ts (JSON-RPC 2.0)
  └─ 6 V0.1 tools + 6 V0.2 tools = 12 tools exposed
  ▼ (MCP protocol)
Claude Desktop / Cursor / Cline / etc.
```

### Storage decisions

- Dedicated Supabase project `france-data-public` (separate from Scopya for clean OSS/commercial isolation)
- PostGIS extension activated for spatial queries (`ST_DWithin`, `ST_Distance`)
- WGS84 projection (`geometry(Point, 4326)`) on all geometric columns
- GIST indices on every geometry column (sub-100ms spatial queries on 1.5M rows expected)
- Estimated total DB footprint: ~230 MB (Supabase free tier offers 500 MB, 2x margin)

### V0.1 tools remain on direct API calls

The 6 tools delivered in V0.1 (`autocomplete_commune`, `get_commune_by_code`, `geocode_adresse`, `reverse_geocode`, `entreprises_in_radius`, `entreprise_by_siren`) keep calling the government APIs (geo.api.gouv, IGN Géoplateforme, recherche-entreprises.api.gouv) directly. There is no benefit to routing them through Supabase, and rewriting them would inflate scope.

## 4. Ingestion pipeline

Each data source has its own GitHub Actions workflow and ingestion script, sharing a common 5-step structure:

```
[1] DOWNLOAD          fetch CSV with retry + identified user-agent
[2] PRE-VALIDATE      file size minimum + expected headers + sample row parses
[3] COPY → STAGING    DROP IF EXISTS + CREATE staging table + COPY in
[4] VALIDATE          row count bounds + null rate on critical columns + Zod sample
[5] ATOMIC SWAP       BEGIN; rename prod→previous, staging→prod, drop old previous; COMMIT
```

If any step throws, the script writes an entry to `ingest_log` with `error_phase` and exits non-zero. The workflow then:

- Surfaces the error in GitHub Actions UI (logs retained 90 days, public)
- Auto-creates a GitHub Issue with label `ingestion-failure` (via `actions/github-script`), triggering an email notification

The production tables are **never** mutated outside step 5, and step 5 is a single transaction. This guarantees no partial-write degradation: the worst case is "yesterday's data is still there".

### Workflow schedule

| Workflow | Cron | Timeout |
|---|---|---|
| `ingest-finess.yml` | `0 4 1,15 * *` (1st & 15th of month, 04:00 UTC) | 15 min |
| `ingest-ameli.yml` | `0 5 * * 1` (Monday 05:00 UTC) | 30 min |
| `ingest-iris.yml` | `0 6 1 1 *` (January 1st 06:00 UTC) | 15 min |

Each workflow also exposes `workflow_dispatch:` for manual trigger from the GitHub UI.

### Required GitHub Secrets

- `SUPABASE_URL` — dedicated project URL
- `SUPABASE_SERVICE_ROLE_KEY` — never committed, never logged (GitHub auto-redacts)

Workflows run only on `cron` and `workflow_dispatch` events, never on `pull_request` — fork PRs cannot exercise the ingestion path or leak secrets.

### Audit trail

`ingest_log` table records every execution with `(source, started_at, finished_at, status, row_count, csv_size_bytes, csv_url, error_phase, error_message, github_run_url)`. Exposed via the optional `data_freshness` query: `SELECT max(finished_at) FROM ingest_log WHERE source=$1 AND status='success'`.

## 5. Database schema

All tables use UTC timestamps and `created_at` defaults.

### `finess`

```sql
CREATE TABLE finess (
  num_finess          CHAR(9)  PRIMARY KEY,
  raison_sociale      TEXT     NOT NULL,
  categorie_code      VARCHAR(4),
  categorie_libelle   TEXT,
  num_voie            VARCHAR(10),
  type_voie           VARCHAR(50),
  voie                TEXT,
  code_postal         CHAR(5),
  code_insee          CHAR(5)  NOT NULL,
  ville               TEXT,
  telephone           VARCHAR(20),
  email               TEXT,
  date_ouverture      DATE,
  date_maj            DATE,
  geom                geometry(Point, 4326),
  raw                 JSONB,
  created_at          TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX finess_geom_gist     ON finess USING GIST (geom);
CREATE INDEX finess_categorie_idx ON finess (categorie_code);
CREATE INDEX finess_dept_idx      ON finess (left(code_insee, 2));
```

### `ameli`

```sql
CREATE TABLE ameli (
  identifiant_pp      VARCHAR(20) PRIMARY KEY,
  nom                 TEXT,
  prenom              TEXT,
  civilite            VARCHAR(10),
  profession_code     VARCHAR(10),
  profession_libelle  TEXT,
  specialite_code     VARCHAR(10),
  specialite_libelle  TEXT,
  mode_exercice       VARCHAR(10),
  conventionnement    VARCHAR(10),
  num_voie            VARCHAR(10),
  type_voie           VARCHAR(50),
  voie                TEXT,
  code_postal         CHAR(5),
  code_insee          CHAR(5),
  ville               TEXT,
  telephone           VARCHAR(20),
  geom                geometry(Point, 4326),
  raw                 JSONB,
  created_at          TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX ameli_geom_gist      ON ameli USING GIST (geom);
CREATE INDEX ameli_specialite_idx ON ameli (specialite_code);
CREATE INDEX ameli_profession_idx ON ameli (profession_code);
CREATE INDEX ameli_dept_idx       ON ameli (left(code_insee, 2));
```

### `iris`

```sql
CREATE TABLE iris (
  code_iris           CHAR(9)  PRIMARY KEY,
  code_insee          CHAR(5)  NOT NULL,
  nom_iris            TEXT,
  type_iris           VARCHAR(2),
  population_totale   INTEGER,
  pop_0_14            INTEGER,
  pop_15_29           INTEGER,
  pop_30_44           INTEGER,
  pop_45_59           INTEGER,
  pop_60_74           INTEGER,
  pop_75_plus         INTEGER,
  pop_csp_agriculteurs   INTEGER,
  pop_csp_artisans       INTEGER,
  pop_csp_cadres         INTEGER,
  pop_csp_intermediaire  INTEGER,
  pop_csp_employes       INTEGER,
  pop_csp_ouvriers       INTEGER,
  pop_csp_retraites      INTEGER,
  pop_csp_autres         INTEGER,
  millesime           SMALLINT,
  geom                geometry(MultiPolygon, 4326),
  centroid            geometry(Point, 4326),
  raw                 JSONB,
  created_at          TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX iris_geom_gist     ON iris USING GIST (geom);
CREATE INDEX iris_centroid_gist ON iris USING GIST (centroid);
CREATE INDEX iris_commune_idx   ON iris (code_insee);
```

The polygon (`geom`) is stored but is **not** returned by V0.2 tools — only `centroid` is used for "around point" queries. This keeps payloads small and leaves room for future "in which IRIS does this point fall" tools without re-ingesting.

### `ingest_log`

```sql
CREATE TABLE ingest_log (
  id              BIGSERIAL PRIMARY KEY,
  source          VARCHAR(20) NOT NULL,
  started_at      TIMESTAMPTZ NOT NULL,
  finished_at     TIMESTAMPTZ,
  status          VARCHAR(20) NOT NULL,
  row_count       INTEGER,
  csv_size_bytes  BIGINT,
  csv_url         TEXT,
  error_phase     VARCHAR(20),
  error_message   TEXT,
  github_run_url  TEXT
);
CREATE INDEX ingest_log_source_started_idx ON ingest_log (source, started_at DESC);
```

### Row Level Security

```sql
ALTER TABLE finess     ENABLE ROW LEVEL SECURITY;
ALTER TABLE ameli      ENABLE ROW LEVEL SECURITY;
ALTER TABLE iris       ENABLE ROW LEVEL SECURITY;
ALTER TABLE ingest_log ENABLE ROW LEVEL SECURITY;

CREATE POLICY "anon read finess"     ON finess     FOR SELECT TO anon USING (true);
CREATE POLICY "anon read ameli"      ON ameli      FOR SELECT TO anon USING (true);
CREATE POLICY "anon read iris"       ON iris       FOR SELECT TO anon USING (true);
CREATE POLICY "anon read ingest_log" ON ingest_log FOR SELECT TO anon USING (true);
```

No INSERT/UPDATE/DELETE policies for `anon` — defaults block. `service_role` bypasses RLS naturally and is used only by the ingestion scripts running inside GitHub Actions.

## 6. MCP tool contracts

All tools follow V0.1 conventions:

- Coordinates accepted in French format (`"49,7724,4,7203"`) or ASCII (`"49.7724,4.7203"`); parsed by the V0.1 helper `parseCoordinates`
- `code_insee` or `commune` accepted as alternate location specifiers (geocoded via V0.1 wrappers if needed)
- `radius_km` defaults to 5, capped at 50, validated with the V0.1 `clamp` helper that throws `RangeError` (improvement listed in V0.2 debt — applied here)
- `limit` defaults to 100, capped at 500
- All Zod-validated inputs and outputs

### Tool 1 — `etablissements_finess_in_radius`

Input: `{ center?, commune?, code_insee?, radius_km?, categories?: string[], limit? }`
Output: `{ count, truncated, results: [{ num_finess, raison_sociale, categorie: { code, libelle, famille }, adresse, coords, distance_km, telephone, email }] }`
Behavior: `ST_DWithin(geom, ST_MakePoint(lon, lat)::geography, radius_km * 1000)`, sorted by distance.

### Tool 2 — `etablissements_finess_by_categorie`

Input: `{ categorie: string, departement?, code_insee?, limit? }`
Output: same shape as tool 1 minus `distance_km`.
Behavior: pure SQL filter, no spatial query.

### Tool 3 — `professionnels_ameli_in_radius`

Input: `{ center?, commune?, code_insee?, radius_km?, professions?, specialites?, modes_exercice?, limit? }`
Output: `{ count, truncated, cgu_notice, results: [{ identifiant_pp, nom, prenom, civilite, profession, specialite, mode_exercice, conventionnement, adresse, coords, distance_km, telephone }] }`
Behavior: `ST_DWithin` + optional filters. **`cgu_notice` is always present** in the response (legal requirement, art. L.1461-2 CSP).

### Tool 4 — `professionnels_ameli_par_specialite_dept`

Input: `{ departement: string, professions?, specialites? }`
Output: `{ cgu_notice, departement, population, resultats: [{ profession, specialite, effectif, densite_pour_100k }] }`
Behavior: `GROUP BY profession_code, specialite_code WHERE left(code_insee, 2) = $1`, density computed against IRIS-aggregated population.

### Tool 5 — `population_iris_around_point`

Input: `{ center?, commune?, code_insee?, radius_km? }`
Output: `{ millesime, iris_count, population_totale, par_age, par_csp, iris_details }`
Behavior: `ST_DWithin(centroid, ...)` selects IRIS, sums population columns. IRIS whose centroid falls in the radius are counted whole — no fine geometric clipping (acceptable for the < 5% target).

### Tool 6 — `panorama_sante_around_point` (composite)

Input: `{ center?, commune?, code_insee?, radius_km?, include?: ("finess" | "ameli" | "iris" | "entreprises_bio")[] }`
Output: `{ query, freshness, cgu_notices, demographie, etablissements_sante: { total, par_famille, top }, professionnels_sante: { total, par_profession, densites_pour_100k }, entreprises_bio? }`
Behavior: `Promise.all` over tools 1, 3, 5 and the V0.1 DINUM call. If a sub-source fails, the response includes `partial: true` and `errors[]` rather than a total failure (mirrors the V0.1 `enrichmentStatus` pattern from commit `f3a9938`).

This is the tool that reproduces the Charleville analysis in a single call — the operational success criterion of V0.2.

## 7. Testing strategy

Three levels:

**Level 1 — Pure unit tests** (≈80% of tests). Vitest with `vi.fn()` mocks. Cover pure functions: `parseCoordinates`, category mapping, Zod schemas, density formulas, pre-ingestion validators. No DB. Sub-second.

**Level 2 — DB integration tests** (≈15%). Vitest against Supabase Local (Docker Postgres + PostGIS). Seed file in `supabase/seed.sql` provides ~20 rows per source clustered around Charleville. Verifies that `ST_DWithin`, `ST_Distance`, joins return the expected results. ~10s setup + <2s per test run.

**Level 3 — Charleville E2E reference test** (1 test). Calls `panorama_sante_around_point` against the seed-loaded local DB and compares the output to `examples/charleville-reference.json`. Tolerance: 5% on counts, 1 unit on small categories like EHPAD count. CI fails if any indicator drifts beyond tolerance — this is the V0.2 release gate.

The reference JSON is established once by manually querying the official sources (FINESS portal, Annuaire Ameli web, INSEE Statistiques locales) and committed.

### V0.1 technical debt remediated alongside

- `api/mcp.test.ts` created — covers `tools/list`, `tools/call` with unknown tool, batch requests, invalid JSON-RPC, non-serializable response payloads
- `src/core/types/branded.ts` introduces `Siren`, `Siret`, `CodeInsee`, `Coordinates` with validating constructors
- V0.2 tools use the branded types; V0.1 tools migrate progressively when their files are touched
- `getEntrepriseBySiren` returns `{ found: true; entreprise } | { found: false; reason; candidates }` instead of opaque `null`
- JSON-RPC error codes corrected: `-32602 Invalid params` for user validation errors, `-32603 Internal error` reserved for genuine server failures

## 8. Delivery plan

Six phases. Each phase ends with something usable end-to-end, not just plumbing for the next.

**Phase 1 — Supabase infrastructure (~1h).** Create dedicated Supabase project, enable PostGIS, configure GitHub Secrets, write base migrations + RLS, install `@supabase/supabase-js` and the Supabase CLI, scaffold `src/storage/supabase.ts` with anon and service clients. Exit criterion: `supabase start` runs locally and migrations apply cleanly.

**Phase 2 — FINESS pilot (~3-4h).** Smallest source first to exercise the full ingestion pipeline on a forgiving volume. Implement `scripts/ingest/finess.ts`, `.github/workflows/ingest-finess.yml` with `workflow_dispatch`, `src/sante/finess-db.ts`, tools 1 and 2 in `api/tools.ts`, level-1 and level-2 tests. Trigger first ingestion manually. Exit criterion: "EHPAD within 5km of Charleville" works through Claude Desktop, deployed to production.

**Phase 3 — Ameli (~3-4h).** `scripts/ingest/ameli.ts`, `ingest-ameli.yml`, `src/sante/ameli-db.ts`, tools 3 and 4. `cgu_notice` always returned. Tests at levels 1 and 2. Exit criterion: cardiologist density in Ardennes is computable.

**Phase 4 — INSEE IRIS (~2-3h).** `scripts/ingest/iris.ts` (CSV + GeoJSON polygons), `ingest-iris.yml`, `src/territoire/iris-db.ts`, tool 5. Tests at levels 1 and 2. Exit criterion: age pyramid around a point retrievable in one call.

**Phase 5 — Composite panorama (~2h).** Tool 6 in `api/tools.ts`, `Promise.all` with partial/error pattern from V0.1 commit `f3a9938`, freshness lookup against `ingest_log`. Write the Charleville E2E test. Freeze `examples/charleville-reference.json` from manual analysis. Exit criterion: "panorama santé Charleville" in one call, < 5% deviations validated.

**Phase 6 — V0.1 debt + finishing (~2h).** `api/mcp.test.ts`, `src/core/types/branded.ts`, progressive migration of V0.2 tools to branded types, JSON-RPC error code fixes, `getEntrepriseBySiren` discriminated union, README + project `CLAUDE.md` + memory updates. Exit criterion: V0.2 publishable, full post-fix discipline chain green on the last commit.

Estimated total: 13-16 hours of dev, spreadable across sessions.

### Why this order

1. Phase 1 is foundational — no Supabase, nothing else works.
2. FINESS before Ameli: smaller (35 MB vs 146 MB), no special CGU handling, validates the full pipeline on a low-stakes volume.
3. IRIS after Ameli: density computation (`effectif / population`) needs Ameli already loaded.
4. Panorama is necessarily last among new tools (it aggregates the others).
5. V0.1 debt is interleaved at the end — it touches existing files and benefits from the V0.2 patterns being settled.

## 9. Risks and mitigations

| # | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| R1 | Government file corrupted or schema-changed | Medium | High | 3-level validation + atomic swap; production table never touched on failure; auto-issue notification |
| R2 | Ameli/FINESS schema evolves silently | Medium | Medium | Integration tests assert expected columns; pipeline fails in pre-validate, never silent |
| R3 | PostGIS query performance > 1s | Low | High (UX) | GIST indices + `ST_DWithin` with `geography` (precise spherical) + strict `LIMIT`; benchmarked in Phase 3 |
| R4 | Supabase free tier saturated (>500 MB) | Low | Medium | Estimated 230 MB cumulative (2x margin); upgrade to Pro $25/month if needed; monitor with `supabase db size` |
| R5 | Ameli CGU notice missing from a response | Low | Legal medium | Unit test asserts `cgu_notice` present in every Ameli response; centralized in `ameli-db.ts` |
| R6 | GitHub Actions cron drifts (DB out of sync with CSV) | Low | Low | `ingest_log` queryable via SQL; optional MCP tool `data_freshness` exposes the last successful import per source |
| R7 | IRIS GeoJSON polygons heavy (hundreds of MB) | Medium | Medium | Stored but not returned by default; only `centroid` used in V0.2 tools |
| R8 | Ingestion duration > 30 min (Ameli 146 MB) | Low | Low | GitHub Actions timeout 30 min; auto-issue on overrun; if recurrent, switch to `actions/upload-artifact` chunking |
| R9 | Ambiguity between `commune` and `code_insee` in tool inputs | Medium | Low | Strict Zod: throw with clear message if both inconsistent or if neither + no `center` |
| R10 | Charleville reproduction fails (>5% deviation) | Medium | High (success criterion) | E2E test red blocks the merge; iterate root cause until green |

### Risks accepted as not-V0.2-mitigated

- Heavy traffic on the public MCP server: no rate limiting in V0.2 (YAGNI). If it becomes a problem, hotfix.
- Adversarial threat modeling: not done formally. Public code + RLS read-only + secrets in GitHub = small surface; sufficient for an OSS project at this stage.

## 10. Implementation decisions deferred to writing-plans

Not blocking design approval; resolved during implementation:

1. CSV download mechanism: `fetch` + stream-to-disk, or `Bun.write` — chosen at code time
2. COPY-into-staging path: native `pg.copyFrom()` (faster) vs batched `supabase.from().insert()` — quick benchmark in Phase 2 decides
3. IRIS centroid source: use INSEE-provided centroid if available, else compute server-side with `ST_Centroid(geom)`
4. Supabase typegen frequency: `supabase gen types typescript` at commit, in pre-commit hook, or in CI — recommendation is pre-commit hook to keep types in sync

## 11. Success criteria summary

V0.2 is mergeable when all three hold:

1. All tests pass at the three levels (unit, DB integration, Charleville E2E)
2. `panorama_sante_around_point({ commune: "Charleville-Mézières", radius_km: 5 })` returns indicators within 5% of the frozen reference
3. The full post-fix discipline chain is clean on the last commit: `/review` LOOP returned no critical issues, `/simplify` ran, docs updated, `tsc` and `pnpm lint` clean

V0.2 is publishable when V0.1 technical debt items listed in Section 7 are also remediated.
